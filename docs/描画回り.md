# class Umtがpaint-previewレイヤー管理クラスそのものです。

重要なメソッド:

```js
place([o,e],T){
  const{tile:A,pixel:L}=this.gm.latLonToTileAndPixel(o,e,this.input.tileZoom),
        I=this.getTileKey(A[0],A[1]);
  let d=this.tiles.get(I);
  if(!d){
    // タイルが無ければ新規レイヤー(Vmt)を作成してmapへaddTo
    const F=..., $=..., re=new Vmt({coordinates:$, id:`${this.id}-${I}`, ...});
    re.addTo(this.input.map);

```

これはwplace側自身が持つUmtという座標→ピクセル配置クラスで、.place(lat, lng, color)を呼べば「タイル未生成なら自動生成し、生成済みなら該当canvasへ直接描く」処理をすべて内包しています。しかもtileSize - L[1] - 1という式がY軸反転そのものです。

このクラスのインスタンスは恐らくwindowグローバルか、Svelteコンポーネントのクロージャ内に保持されています。placeメソッドを直接呼べれば、私たちが手動で座標変換・canvas直描画・タイル管理をする必要が一切なくなります。このインスタンスへの参照を探します。

const ze = new Umt({...})が発見できました。このze変数がSvelteコンポーネントのローカル変数です。これは難読化された変数名で、モジュールスコープのグローバルではなくコンポーネント内クロージャに閉じ込められているため、外部から直接アクセスするのは難しいです。

しかし、ze.place(...)が呼ばれる箇所（実際のクリックハンドラ内）を見つければ、そのクリックハンドラがwindowやイベントにzeをどう露出しているか、あるいはze.placeをどう呼んでいるかが分かります。.place(の呼び出し箇所を検索します。

決定的な情報が得られました。1681950の箇所が実際のクリックハンドラです:

```js
ze.place(sr, Br); // sr = [lat, lng], Br = colorIdx
```

ze.place([lat, lng], colorIdx) — 緯度経度とcolorIdxを渡すだけでよく、内部でタイル/ピクセル座標変換・canvas生成・Y軸反転・描画・play()トリガーを全部やってくれる、まさに理想的なAPIです。このzeはUmtインスタンスで、Svelteコンポーネントのクロージャ内にあります。外部からこれを呼び出すには、window.mrWplace.paintedPixelMapと同じ方法で、内部の何らかのグローバル参照から辿るか、または関数をフックする必要があります。

ze自体はグローバルではありませんが、これを含む関数（クリックハンドラ）をmap.on("click", ...)のように登録している箇所があるはずです。その周辺でクロージャ変数への到達方法を探ります。

非常に重要な発見が2つあります:

1. He(Kt, Br, Ln=!0) がまさに求めていた関数です（Kt=座標配列、Br=colorIdx、Ln=履歴保存フラグ）:

```js
function He(Kt, Br, Ln=!0) {
  for (let sr of Kt) {

    const to={color:oi,tile:On,pixel:Gi,season:o.season,colorIdx:Br};
    const zi=Qg(to); // キー生成 (これが t=(...) 形式)
    const Ai=F.get(zi); // F = 予約Map (=targetPaintedPixelMap相当)
    // charges消費チェック

      F.set(zi,to); // Map書き込み (これが今フックしているもの)
      ze.place(sr,Br); // ★ここがcanvas描画 + タイル自動生成
      o.crosshair.place(sr);
      if(Ln) ut.saveAction(...); // undo履歴
    }

  j(re,F.size,!0); // charges残数のUI更新
  // ネットワーク送信 (Bt = fetch)

```

2. mo=c(me)-F.size が charges 消費ロジックです。F.size（Map内のエントリ数）がその場でchargesを消費する仕組みになっており、F.set()（=targetPaintedPixelMap.set()）を呼んだ時点でMap.sizeが増え、それだけでchargesがUI上「消費された」ように表示される可能性が高いです。つまり私たちが直接.set()しているのは、実質的にHe()関数の一部だけを再現している状態で、ze.place(sr, Br)（描画）とj(re, F.size, !0)（charges UI更新）を呼んでいないため画面に何も表示されないのです。
