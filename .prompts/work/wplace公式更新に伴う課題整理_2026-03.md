# WPlace 公式更新に伴う課題整理

## 目的

WPlace 側の機能更新により、Mr. Wplace の存在意義・互換性・今後の方針が揺れている。
このメモは、頭の中にある問題を以下の 3 つに分けて整理するためのもの。

- 今すぐ直さないと使い物にならない問題
- 方向性を決めないと実装がぶれる問題
- 差別化要素として残すか、公式へ寄せるかを判断する問題

## 現状の認識

WPlace 公式が、これまで拡張機能側の価値だった機能を一部取り込み始めている。
特に影響が大きいのは以下。

- 公式がギャラリー機能を持った
- 公式がオーバーレイ機能を持った
- 公式独自の共有形式 `.wplace` がある

これにより、Mr. Wplace は「公式と競合する独自機能の塊」のままだと維持コストが上がる。
一方で、進捗カウントのように依然として拡張機能側にしかない価値も残っている。

## 課題一覧

### 1. クリティカル: オーバーレイ追加時のエラー

症状:

- 新しいソースレイヤーを追加しようとするとエラーが出る
- 新しいソースレイヤーを参照できない系のエラーに見える

意味:

- 現在の中核機能が壊れている可能性が高い
- 方針議論より先に、最低限ここを調査しないと評価も比較もできない

仮説:

- `addSource` と `addLayer` の順序・タイミングが公式更新で噛み合わなくなった
- 参照先レイヤー ID / beforeId / pixel-hover 周辺のレイヤー構成が公式更新で変わった
- style reload 後に source/layer の再登録が崩れている
- 公式オーバーレイ追加によって、既存の layer/source 名や期待順序が競合している

### 2. 戦略課題: 公式ギャラリーとの関係

問題:

- 公式にもギャラリーがあり、UI 上の役割が重なっている
- 同じ場所で別々のギャラリーが出ると UX が悪い

取りうる方向:

- A. 相互同期する
- B. 公式ギャラリーへ寄せて、拡張機能側は補助に回る
- C. 拡張機能ギャラリーを独自高機能路線として維持する

評価:

- A は理想だが、解析コストが高い
- B は保守コストを下げやすい
- C は差別化できるが、公式と二重管理になりやすい

現時点の推奨:

- **短期は B 寄り**
- ただし、公式ギャラリーへ完全移行できる保証がないため、拡張機能側ギャラリーはすぐには捨てない
- まず「どこまで公式に寄せられるか」を調査し、その結果次第で A か B を選ぶ

### 3. 互換性課題: `.wplace` 形式への対応

問題:

- これまでは「画像 + ファイル名に座標を埋める」形で共有していた
- 公式は `.wplace` という JSON ベース形式を持っている

必要そうな対応候補:

- `.wplace` を読み込める
- `.wplace` と既存形式を相互変換できる
- `.wplace` を出力できる

優先度の考え方:

- 読み込み対応の方が先
- 出力は後でもよい

理由:

- まずは公式エコシステムとの接続が必要
- 読み込みだけでもユーザーの実用性はかなり上がる
- 出力までやると仕様の理解と検証コストが大きくなる

現状:

- **import は実装済み**
- **image detail からの `.wplace` export も実装済み**
- ただし export は最小互換であり、`dithering` など一部メタデータは固定値出力

### 4. 発展課題: 公式オーバーレイの拡張

アイデア:

- 公式のオーバーレイ機能を土台にして、拡張機能が編集・色変換・ディザリングなどを追加する

魅力:

- 公式の UI / 保存形式 / 将来性に乗れる可能性がある
- 自前オーバーレイの維持コストを減らせる可能性がある

リスク:

- 公式実装の解析コストが高い
- そもそも拡張可能とは限らない
- DOM/内部状態依存になりやすく、更新耐性が低い

現時点の結論:

- **今すぐ本線にしない**
- 先に feasibility 調査だけ行う
- 「できる」と確認できるまでは、戦略候補の 1 つとして保留にする

### 5. 差別化候補: 進捗カウント

内容:

- 背景タイルとオーバーレイ画像の色比較を行い、完成率や一致数を出す機能

認識:

- 計算コストが高い
- だからこそ公式は未実装、または意図的に避けている可能性がある

意味:

- これは依然として Mr. Wplace の独自価値になりうる
- ただし、高頻度計算や全体計算をそのまま押し出すと重い

方針:

- 「公式へ寄せる対象」ではなく、「拡張機能の差別化機能」として扱う
- ただし常時計算ではなく、必要時のみ計算・範囲限定・キャッシュ前提で考える

## 問題を混ぜないための整理

今の混乱の原因は、性質の違う問題が同時に頭に入っていること。
以下の 3 レーンに分けると整理しやすい。

### レーン 1: 壊れているものを直す

- オーバーレイ source/layer エラーの調査
- 既存機能が公式更新でどこ壊れたか確認

### レーン 2: 公式との接続を作る

- 公式ギャラリーの調査
- `.wplace` 形式の調査
- どこまで公式に寄せられるか確認

### レーン 3: 独自価値を残す

- 進捗カウント
- 高度な画像変換
- 公式では重くて入れにくい補助機能

## 推奨方針

現時点では、以下の方針が最も現実的。

### 方針の核

- **短期は「壊れた主機能の復旧」を最優先**
- **中期は「公式との互換性確保」を優先**
- **長期は「独自価値だけを残す」方向に寄せる**

### つまりどうするか

- オーバーレイが壊れているなら最優先で直す
- ギャラリーは独自路線を伸ばす前に、公式との関係を定義する
- 共有形式は、まず公式の読み込み対応を目指す
- 進捗カウントは、独自価値として磨く候補に残す
- 公式オーバーレイ拡張は、調査結果が出るまで本開発しない

## 実行順

### Phase 1. 緊急安定化

やること:

- オーバーレイ source/layer エラーの再現
- エラー発生箇所の特定
- 公式更新で変わった layer/source 構成の確認
- 最小修正で overlay 表示を復旧

この Phase のゴール:

- 少なくとも既存の overlay が再び使える
- 以後の比較検討を進められる状態に戻す

### Phase 2. 仕様調査

やること:

- 公式ギャラリーのデータ構造・保存場所・ UI 導線を確認
- `.wplace` の JSON 構造を確認
- 公式オーバーレイがどこまでフック可能か確認

この Phase のゴール:

- 「同期できそうか」「寄せられそうか」「無理そうか」を判断できる

### Phase 3. 方針決定

判断すること:

- ギャラリーは同期するのか
- 公式 UI に寄せるのか
- 既存ギャラリーを縮退させるのか
- `.wplace` は import のみか、export までやるか

この Phase の成果物:

- 1 枚の方針メモ
- やらないことの明文化

### Phase 4. 実装

有力な順:

- ギャラリー連携または縮退
- 進捗カウント改善

完了済み:

- `.wplace` import 対応
- image detail からの `.wplace` / PNG 選択 export 対応

## 最初の 1 週間でやるべきこと

優先順はこれでよい。

1. オーバーレイエラーの原因特定と復旧
2. 公式の layer/source/UI 構成の調査メモ作成
3. `.wplace` のサンプル確保と構造把握
4. ギャラリーを「同期」「寄せる」「独自維持」のどれにするか仮決定

## 今決めなくてよいこと

以下は今すぐ結論を出さなくてよい。

- 公式オーバーレイ拡張を本当にやるか
- 進捗カウントを公式に寄せるべきか
- 既存ギャラリー UI を完全に捨てるか
- `.wplace` export をいつやるか

先に事実確認が必要。

## 意思決定の基準

迷ったら、以下の順で判断する。

1. まず今のユーザーが困っているか
2. 公式更新で壊れやすい実装にならないか
3. 保守コストに見合うか
4. Mr. Wplace にしか出せない価値か

## 現時点の暫定結論

- 一番先にやるべきなのは overlay 復旧
- 次にやるべきなのは、公式ギャラリーと `.wplace` の調査
- 戦略としては、短期的には **公式に寄せる方向を強める** のが安全
- ただし、進捗カウントのような独自価値は残す余地が大きい
- 公式オーバーレイ拡張は夢があるが、今は調査対象であって主戦略ではない

## 2026-03-17 追記: 暫定安定化の判断

現時点では「overlay 復旧」より前に、まず壊れる経路を閉じる判断を入れた。

- 理由:
  - custom `geojson` source 追加で Wplace 側が非同期エラーを起こす
  - 失敗時に map 全体の再読込や表示不安定化を巻き込む
  - 後段で頑張るより、起動時にその機能群を disable する方が安全

- 一時停止したもの:
  - pixel grid
  - area display / area edit
  - 独立 overlay の paint guide 丸

- 維持したもの:
  - 独立 overlay 本体の raster layer
  - area manager modal の導線

- UI 方針:
  - `ピクセルグリッド` と `エリア表示` は off のまま disabled
  - ただし area manager modal は開ける

この判断は「根本修正」ではなく「緊急安定化」に属する。
少なくとも今は、GeoJSON 依存の custom layer を前提にした設計で前進しない方がよい。

## 次アクション

2. 公式更新後の map layer 構造を確認する
3. `.wplace` サンプルを 1 つ確保して import 観点で読む
4. その結果を元に、ギャラリー方針を 3 択から 1 つに絞る
